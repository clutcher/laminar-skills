# Design a change

You design the code of a change before any code is written: its classes and methods, its folders, and the owner of each decision. You write 1 design model by `references/design-model.md`, `references/design-decisions.md` and `references/design-boundaries.md`. Scripts check it and render it as `design.md`, writer agents write the code from it, and the review of the result shows whether the design reached its aim, which is a review with nothing to report on the change. You write no production code yourself and report no finding of your own. The book: "These questions check the planned structure the same way they check existing code, because the failures they target are cognitive rather than structural." (*How to Apply the Principles*, *How to Apply the Principles to New Code*)

Contents: 1. The 2 modes · 2. The input · 3. The results folder · 4. The procedure · 5. What this skill does not do · 6. The reference files

## 1. The 2 modes

The skill runs in 1 of 2 modes. Say the mode in your first line.

- The mode with a user, the default: you ask the user each question of the model (`AskUserQuestion`, in Claude Code), and the user approves `design.md` and the migration before any writer runs.
- Autonomous mode, where the input asks for it, such as with `mode: autonomous`: you ask nothing, and each question takes the answer that its key `autonomous` states. A question whose `autonomous` is `default` takes its recommendation, for every kind of question, and `design.md` prints it as a decision taken by default; for a failure policy, the recommendation is the first choice of the failure line that fits the I/O execution (`references/designing.md`, section 10). Only a change of an existing output that a program outside the application reads takes `stop`, because such an output never changes without a user: it stops the run before any writer runs, and the design and the question are then the result. The form of a new output, such as the status code of a new failure or the fields of a new response, is no question: you decide it and write it in the model (`references/design-boundaries.md`, `entries`). A threshold or a boundary between applications stays open, and no writer writes code across it. The change forecaster answers depth. A finding of a review run or an item of a shape run stays unfixed only as `outside the change`, where git or the design check shows that the change did not touch its cause, or as `project convention`; every other reason becomes a question. In the loop of step 12, the round script checks these 2 dispositions of each finding of a round (`references/design-rounds.md`). A defect of an existing field or member of a modified class is inside the change and takes no reason class: you fix it, and the migration carries the fix in a migration group of its own (`references/design-findings.md`, `existingDefects`); in the mode with a user it is a question whose recommendation is the fix. So autonomous mode can end in a question for the user, and it never passes a question in silence: `design.md` prints each answer that no user gave.

## 2. The input

Read what the user gives (`$ARGUMENTS`, in Claude Code), and say in 1 short line what you got:

- A described change: free text with ideas, such as a feature, a ticket or a folder structure, or a plan file, such as one written in the plan mode of Claude Code. Its scope is the folders that its words and its file names touch, which you find in the repository.
- The run folder of a run of the skill `review` of the plugin laminar, as signals. Read 3 files of it and no other: `review.md` for the numbered items and the scope line, `review.sarif` for the abstraction, scale and places of each finding, and `review-evidence.md` for the evidence and the `Cause:` lines. Its scope is the files the findings name and their folders. Every item of `review.md` at the application, module and class scales must be closed by the model, or left on purpose with 1 reason class of section 4, step 3. Read the method and variable findings of the same files as signs of the cause.

A run folder may come with a described change. The redesign of a folder or a module with no run folder and no described change comes in a later version: for it, ask the user for a described change, or for a run of the skill `review` on that folder first.

## 3. The results folder

The results folder holds `design-model.json`, `design.md`, `migration.md`, `base-commit.txt`, the run folders of the shape runs under `shape-runs/`, and the record of each round of the loop under `rounds/<n>/`. The user may name it as `results: <path>`; else create a new temporary folder outside the repository. Name it in your first line. You write nothing into the repository; only the writers do. Read the repository itself, and never a review worktree under `.claude/worktrees/` of it, because a worktree holds another head of the same code, and code found there would steer the design.

## 4. The procedure

The paths of the scripts are relative to the folder of this skill, and `<review skill>` is the folder of the skill `review`, `../review` from here.

1. Read the input and find its scope. Read the project conventions as the skill `check-conventions` finds them: each `.md` file under `.claude/rules/conventions/` of the repository whose `paths:` match a folder of the scope, and each file there with no `paths:`. A project convention may set the zones and their zone order, the naming grammar, the folder layout and the test file suffixes. It overrides a rule marked narrower than the book, and never a format of this skill or a design direction of the book.
2. Read the current code of the scope, the private members included, by `references/designing.md`, section 1, and the 5 reference files of section 6.
3. For a run folder, ask of each finding whether it holds and what its cause is, on the code at the head and at the base of the reviewed range. A finding whose behavior the docs or the tests record as intended still holds. A finding stays unfixed only with 1 reason class of this closed set, never because you think it wrong and never because the repository repeats the form: `outside the change`, where the change did not touch its cause lines; `question to the author`, where the right shape rests on a fact the code does not show; `project convention`, where it rests on a rule marked narrower than the book and a conventions file of the project covers it; `exempt by the book`, where the book itself states the exemption, quoted with its chapter and section in italics, which also tells the maintainer of the plugin, because a finding against a sentence of the book is a defect of the review; and `fix apart`, where its fix reaches code outside the change in several modules. List every finding of 1 folder, at every scale, before you answer any of them, because a method finding often names the cause that a module finding only shows. Write 1 object of `decisions.findings` for each item at the application, module and class scales, with the part that closes it or its reason class (`references/design-decisions.md`).
4. Pass 1, the tree. Write the shape half from the outside in, by `references/designing.md`, sections 2 to 8: the owners first, then the parts until every operation is a part, then the signatures, then the folders. Write `decisions.owners`. Start the change forecaster, the agent `design-forecaster` of the plugin (`laminar:design-forecaster`, in Claude Code), by `references/forecaster.md` once on this draft, and decide depth from its answer; where a later shape run adds owners, start it again on the added owners only. Write `decisions.exits` by `references/designing.md`, section 10, because the failure line of each I/O execution decides its return type. Then run the design check alone, `scripts/checkDesign.mjs` with the options of step 7, on this model and fix each defect it prints before the first shape check, other than the keys of pass 2, which it prints as missing: it costs no agent call and finds defects that would cost a shape run (`references/design-checks.md`, section 1).
5. Run the shape check on the tree. The prepare command reads the shape half of the design model and ignores the rest, so pass the model itself: `node "<review skill>/scripts/runReview.mjs" prepare --run "<results>/shape-runs/<n>" --repo "<repository>" --shape "<results>/design-model.json"`, where `<n>` counts the shape runs from 1. Then run the judge workflow, the merge and the render of the skill `review`, as its steps 2 to 5 say. Run the merge and the render also on a run that keeps nothing, so its run folder holds `review.md` and `review.sarif`. After each shape run, report its measured cost, the judge workflow and the verify workflow together, as the host reports the use of each workflow; never report the cost plan of the prepare command as the cost, because it leaves out the verify workflow. Change the tree for each kept item and run the shape check again, until every kept item is closed by the tree or holds a reason class under `decisions.findings` (`references/design-findings.md`). Where the input states a ceiling, it counts shape runs, never dollars. The ceiling limits the shape runs, never the judging: where the tree changes after the last shape run the ceiling allows, run 1 shape check after the ceiling, a shape check of the changed items alone, each at its own scale (`--scales module|class|method --paths <files>` on the prepare command, with the scales of the changed folders, classes and methods), which counts as no shape run. Else leave each item that the change would close open, as `openAfterCeiling` with the intended change as its text (`references/design-findings.md`), keep the tree as the last shape run judged it, and `design.md` lists the item under `Open after the ceiling`. The parent folder of each folder that the change creates or moves stands in the shape half as a `modified` folder, because it gains a child. A class whose public members change gets a shape run also where it stays in its file. A method that coordinates 2 or more parts carries its `body` as the calls in order, and a method that does I/O carries its I/O line and its failure line, the same choice as its object under `exits`, so the judges read them before any code exists. Where the change creates, moves and removes no file and no folder and changes no public member, the shape check is not needed; say so with the reason. Where depth changes after the shape check passed, run the shape check again on the changed part only. In a host where the shape check cannot run, such as GitHub Copilot CLI, ask the detection questions of the 6 cognitive failures about each folder, class and signature yourself, and mark each answer as not checked by the review.
6. Pass 2, the decisions on the tree that passed: `decisions.conventions`, the `placement` of each owner, then `entries` with the `responses` of each entry, `tests` and `questions`, in the form of `references/design-decisions.md` and `references/design-boundaries.md`, by `references/designing.md`, sections 9, 11 and 13. Each question names the fact the code does not show, gives 2 or more options, each with its tree or its signatures, and a recommendation; an option that brings back the failure it was meant to close is no option.
7. Run the finish command on the whole model, `node scripts/finishModel.mjs --model "<results>/design-model.json" --repo "<repository>" --results "<results>"`, and add `--review "<run folder>/review.md"` where the input is a run folder, and `--shape-review "<results>/shape-runs/<n>/review.md"` once per shape run. It runs in order the design check, `scripts/checkDesign.mjs`, the render, `scripts/renderDesign.mjs`, and the migration script, `scripts/planMigration.mjs`, passes each the options it takes, and stops at the first of them that prints a defect or fails, with the name of that script and its output; the 3 scripts may still run alone, with the options of their usage line. Fix each defect it prints, and run it again. Recheck each recheck case it prints against the model; where the model shows that a case is wrong, write it as 1 object of `decisions.scriptCases` with its code, its display name and its text, so `design.md` shows it as a defect of the script (`references/design-findings.md`).
8. The finish command renders `design.md` into the results folder once the design check passes. Never write `design.md` by hand.
9. Ask the user the questions of the model, and write each answer under `answer`. Where an answer changes the shape half, run step 5 on the changed part. Then run steps 7 and 8 again, and show `design.md`. In autonomous mode, apply section 1 instead.
10. Set `group` on each class that the change creates, moves, renames, modifies or removes, and on no class of an `unchanged` file, by the boundary the classes share: an abstraction, a folder or a decision, and the narrower one where 2 fit, so the abstraction comes before its folder and the folder before the decision (`references/design-model.md`, section 3). Write the migration by running the finish command of step 7 again, which writes `<results>/migration.md`; for the steps as JSON, run `scripts/planMigration.mjs` alone with an `--out` path that ends in `.json`. The migration script writes the steps per migration group in the order of the group numbers, and inside each group in 7 stages: folders, moves and renames, created classes, changed members, bodies, removals, and then tests (`references/design-checks.md`, section 5). In the mode with a user, wait until the user approves `design.md` and the migration.
11. Before the first writer runs, write the commit id of the head of the repository into `<results>/base-commit.txt`: it is the base commit of the change. Start the writers with the writer workflow (`Workflow({ name: "laminar:laminar-design-writers", args: { results: "<results>" } })`). It reads `<results>/migration.workflow.js`, which the migration script writes beside the migration, starts 1 writer per migration group, the agent `design-writer` of the plugin (`laminar:design-writer`, in Claude Code), with the inputs of `references/writer.md`, each group after every earlier group it touches and the others side by side, and returns for each group its `outcome` (`finished`, `stopped`, `not started` or `no answer`), its `files`, its `commitMessage`, its `build`, its `tests` and its `stop`. Its writers commit nothing, so commit each finished group with its files and its commit message, in the order of the group numbers. In a host with no Workflow tool, start 1 writer for each migration group, in order, by `references/writer.md`; where the host lets a subagent write git, the writer makes 1 commit for its group, and where the host refuses it, such as by a hook, you commit that group with the message the writer returns before you start the next writer. Record each stop under `decisions.stops`, change the model, run the checks of steps 5 and 7 on the changed part, where the design check reads the tree of the base commit and not the files of the writer (`references/design-checks.md`, section 1), render again and start the writer again on the files that the writer before it left uncommitted: call the writer workflow again with `groups`, the list of the stopped and not started groups, and `leftFiles`, the files of each stopped group by its number; commit the group only when a writer finishes it. Where the writer stops a second time on the same abstraction, ask the user a question about it in place of a third start; in autonomous mode, end the run with that stop as its result.
12. Run the loop of rounds by `references/design-rounds.md`. A round is the review of the code of the writers and the dispositions of its findings. Round 1 runs the skill `review` with `--range "<base commit>..HEAD"` and `--scales application,module,class` on its prepare command; a later round reviews from the head of the round before, or from the base commit again where the fixes moved, created or split a file, and widens the range so that it judges each finding key the round script lists as `still open`. Write 1 disposition per finding: to the designer where the fix changes the tree, a signature or a placement, and always for a finding at the application or module scale; to the writer of the migration group that owns the class where the fix stays inside a body; `outside the change` or `project convention`; or closed by an answered question, which names the question; in the mode with a user, also `question to the author`, `exempt by the book` or `fix apart`. Then run the round script, `node scripts/recordRound.mjs --results "<results>" --run "<run folder>" --dispositions "<file>" --model "<results>/design-model.json" --repo "<repository>"`, with `--autonomous` in autonomous mode. Its loop line decides: `pass` ends the loop, and you report the items in the change and the measured cost of the shape runs and of each round; `stop` ends it with its code and text, and in the mode with a user you ask the user, with the counts and the dollars so far; `continue` applies the dispositions. The designer changes the model and never code, runs the class check on the changed classes, the design check and the render, and plans the migration of the round; each writer gets each finding sent to it as 1 step of its brief and never edits the model. Then the next round starts. A ceiling of rounds stands only where the input states it, never as a default; where the round reaches it, the loop line is `stop ceiling-reached`.

## 5. What this skill does not do

- It is not a review. It reports no finding of its own, gives no finding a severity and does not rank the findings.
- It is not a bug fix. A finding that names wrong behavior is fixed as a bug fix (the skill `code-style`, section 1), and only where the fix keeps every output that a user or another system reads. A change of such an output, such as a fail-fast fix that changes an exit code or the result of a gate, is a question to the user, never a silent fix (`references/designing.md`, section 13).
- It takes no finding of another review skill as input, such as one that looks for bugs; name such a finding and leave it out.
- It decides no fact that the code does not show, such as a threshold or where a boundary between applications runs; it asks the user, because "Which depth is right is a question about how the system will change, not something you can read from the code in front of you." (*The Encapsulation Principle*, *Depth Is a Design Decision*)

## 6. The reference files

Each path is relative to the folder of this skill. The designer does not load the skill `code-style`; it reads these sections of its reference files, which hold the design directions of the shape: `../code-style/references/naming.md`, sections 1, 3, 8 and 9; `../code-style/references/classes.md`, sections 1, 2, 4, 5, 6, 8 and 9; `../code-style/references/modules.md`, sections 1, 2, 3, 4, 5, 8, 9 and 11; `../code-style/references/correctness.md`, sections 1, 2, 3, 8 and 10; and `../code-style/references/tests.md`, sections 3, 4, 5 and 12. Where the skill `code-style` is loaded in the session anyway, such as by a hook of the plugin before a first write, the designer still takes its rules from these sections alone. It reads the conventions file of each language of the scope, such as `../code-style/conventions/java.md`, only for the names of files and classes and for the forms of test names.

- `references/design-model.md`: the form of the design model as a whole, the order of work, the shape half and its keys beside the shape model, the change marks, and which script reads which key; read before you write the model.
- `references/design-checks.md`: what the design check reports, the zone order, the cycle check, and how the migration script orders its steps; read at steps 4, 7 and 10.
- `references/design-decisions.md`: the keys `conventions`, `owners` with `forecast` and `questions` of `decisions`, and which script reads each; read at steps 4 and 6.
- `references/design-findings.md`: the keys `findings`, `stops`, `existingDefects` and `scriptCases` of `decisions`, filled from the items of the review and the shape runs, the existing defects of a modified class, the recheck cases and the stops of the writer; read at steps 3, 5, 7 and 11.
- `references/design-boundaries.md`: the keys `entries`, `exits` with the failure line, and `tests` of `decisions`, the decisions of each boundary, and which script reads each; read at steps 4 and 6.
- `references/designing.md`: the rules of procedure of the designer; read at steps 2, 4 and 6.
- `references/forecaster.md`: the inputs of the change forecaster and what the designer does with its answer; read at step 4.
- `references/writer.md`: the inputs of the writer and what the designer does with a stop; read at steps 11 and 12.
- `references/design-rounds.md`: the rounds of the loop, the dispositions, the round script with its counts, its comparison and its loop line, and the migration of a round; read at step 12.
- `../review/shape-model.md`: the shape half, as the shape check reads it.
