# The inputs of the writer

Contents: 1. When it runs · 2. What it gets · 3. The agent · 4. What the designer does with a stop · 5. The self-check of each group · 6. The build after the last group

## 1. When it runs

The session that runs the plan starts 1 writer for each migration group, after the plan ended with the outcome `ready`: a calling session, or a plain session by `SKILL.md`, section 5. In Claude Code, the writer workflow `laminar:laminar-design-writers` starts them: it reads `migration.workflow.js`, which the migration script writes beside the migration, starts each migration group after every earlier group it touches, because a later migration group builds on the code of an earlier one, and starts the groups that touch no earlier group side by side. 2 groups touch where a step of each lists the same file or a file under a folder the other lists, or where a class of one names a class of the other. Each writer runs as the agent type `laminar:design-writer`, whose file holds the rules of the writer (section 3), and its prompt holds only the inputs of section 2. In a host with no Workflow tool, start each writer as 1 subagent by section 3, in the order of the migration, and start the next one only after the one before it returned. In a host with no subagent, the session follows the body of the writer itself.

## 2. What it gets

- The path of `design.md` and of the migration, and the number of its migration group, whose steps alone it writes.
- The path of the repository.
- The open questions of the model whose `autonomous` is `open`, so the writer knows which code it may not write.
- Where a writer of the same migration group stopped before, the files it changed and left uncommitted, which this writer goes on from.
- Where the plan came from a run folder, the path of its `review.md`, whose findings the finding steps of the migration group name (`design-rounds.md`).
- In the answer round only, the path of `review.md` of the self-check of its group, whose kept findings it answers once (section 5).
- Only where the call of the writer workflow gives `build: "after-the-last-group"`, the line that it builds nothing, and in a fix call the path of the output of the failed build (section 6).

The writer workflow gives each input on its own line, in this order: `Design:`, `Migration:`, `Migration group:`, `Repository:`, `Open questions:`, `Files left by the writer before:`, `Review of the round:` only where the plan came from a run folder, `Self-check:` only in the answer round, `Build:` and `Build failures:` only by section 6, and `Commit: by the session`. The last line is the same for every writer, because writers that run side by side share 1 index of git.

## 3. The agent

The fixed rules of the writer stand in its agent file, `agents/design/design-writer.md` of the plugin, which is `../../agents/design/design-writer.md` from the folder of this skill: it loads the skill `code-style` of the plugin laminar once before it writes, keeps every name of `design.md` and the conventions of `decisions.conventions` with their test name forms, writes the steps of its migration group in order, builds and runs the tests, and returns its files and its commit message, or 1 stop of a closed list of reasons. Where its message holds `Build: after the last group`, it builds nothing and runs no test (section 6). In Claude Code, the writer workflow starts it as the agent type `laminar:design-writer`, whose file pins its model, its effort and its tools. In a host with no agent of the plugin, start 1 subagent with the body of that file, below its frontmatter, as the start of its prompt, then the inputs of section 2.

The writer commits nothing, because the writer workflow gives every writer `Commit: by the session`; a session that starts a writer without the writer workflow gives it the same line. The writer returns its files and a commit message, and the session that runs the plan commits each finished migration group with that message. The review after the writers reads the range from the base commit to the head (`SKILL.md`, section 5).

## 4. What the designer does with a stop

The session that runs the plan passes each stop to the next call of the skill as `stop: <file>`, with the group and the files the writer left uncommitted, and the start command writes it as 1 object of `decisions.stops`, with the `plan` of the writer. A stop sends the abstraction it names back to the designer: change the model, run the shape check on the changed part where the shape half changed, and run the finish command, whose cut migration plans the stopped group whole. The designer answers a stop only after the reads of `SKILL.md`, section 7, because the fix of a stop writes a name, a signature or a body, and it lists those files under `decisions.referencesRead`. The files of the writer that stopped stay uncommitted, and the next writer of that group goes on from them. A writer that stops with no stop of its own, or gives no answer, gets the stop `stopped-without-a-reason` from the writer workflow, at the first class of its group, so every unfinished group reaches the next plan. A group whose writer finished with a failed build gets the stop `build-failed` from the writer workflow, with the failing build command as `says`. A group whose writer finished with a build that did not fail and a test command that failed, or that ran no test where the migration gives the group test steps, gets the stop `tests-failed`, with each such command as `says`. Each stop stands at the first class of the group, else at `migration group <n>`, so the session commits nothing of the group, no group that waits for it starts, and the next plan takes the group as stopped. A session that commits group by group calls the writer workflow once per group with `groups: [<n>]`, because 2 groups that share a file finish in 1 call, and the files of one then hold the lines of the other. The group is committed only when a writer finishes it with a build that did not fail and tests that passed. Where the writer stops a second time on the same abstraction, ask the user a question about it, with the 2 stops as its fact, in place of a third start; in autonomous mode, the start command ends the plan with that stop as its outcome. The writer never decides a design problem alone, because a shape it chose would reach the review with no check before it.

- Book (*How to Verify Correctness*, *How to Produce Verified Code*): "Writing code often reveals design problems, so the developer returns to thinking, adjusts the decisions, and updates the code to match."

## 5. The self-check of each group

The writer workflow runs 1 self-check on each group that its writer finished with a build that passed or no build step, and with tests that passed, before the session commits the group, unless its call gives `selfCheck: false`. With the argument `build: "after-the-last-group"`, the writer runs no test, so a group with no failed build and no failed test is enough (section 6). The self-check is a run of the skill `review` on the files of the group against the head, read by the extract input `--uncommitted`, with the decision, method, variable and test-method judges, the refuter and the verifier, in the run folder `<results>/plans/<n>/self-check/group-<g>`. The agent `design-self-check` of the plugin (`laminar:design-self-check`, in Claude Code) runs its commands, because a workflow runs no command and writes no file. The writer of the group then answers each kept finding once, in 1 answer round: fixed inside the bodies or the tests of its group, or recorded with 1 record reason, `changes-the-model`, `outside-the-group`, `rule-says-otherwise` or `fix-breaks-the-build`. Its fixes are not judged again before the commit, and no group gets a second self-check, because the closing review of the round judges every scale anyway. An item to consider goes to the record with no answer, because it waits for the author.

Before the writers run, state the self-check share of each group from the line `Self-check: judge calls about <k> · dollars about $<d>` under the heading of the group in the migration, beside the cost of the writers; the group that writes the tests carries the largest share. A self-check whose cost line passes the threshold of the cost check of the review does not run, because that check asks a person. A self-check never fails its group: where it does not run or stops, the group still finishes, and `selfCheck.notRun` gives the reason.

After the writer workflow returns, write `selfCheck` of each group into `<results>/plans/<n>/self-check.json`, a JSON list with 1 object per group, `{"group": <g>, ...selfCheck}`, then commit the groups as before. `needsModelChange` lists each kept finding that the writer recorded `changes-the-model`; this skill does not read it, and the designer meets such a finding again in the closing review of the round, which raises the same key on code that still stands. A calling session that wants the next plan to answer it passes it in the input `stop: <file>` as the answer of a committed group, 1 object `{"group": <g>, "committed": true, "stop": {"reason": "fix-changes-the-model", "at": <display name of the finding>, "says": <says of the answer>}, "leftFiles": []}`. The start command records it under `decisions.stops` with `committed: true`, and the designer answers it first, as a stop. Its group stays finished, so the next plan carries its written classes as written, plans the group again only where the designer changes one of its classes, and gives each finding that its steps fixed the no-step line `fixed by plan <n> group <g>`. The render with `--rounds` prints 1 line per group of each plan under the rows of `## Rounds`: the judge calls, kept, fixed, recorded by reason, unanswered and to consider, or the reason it did not run.

The search of a self-check also reads the files that are untracked and not ignored, so a group finds the other place of a rule in a file that an earlier group of the same call wrote and the session did not commit yet. The closing review drops no judge.

## 6. The build after the last group

The argument `build` of the writer workflow takes 2 values. `per-group` is the default: each writer builds and runs the tests of its own group, as sections 3 to 5 say. With `after-the-last-group`, each writer gets the line `Build: after the last group` and builds nothing, and the writer workflow runs 1 build of the round after every group and every self-check of the call finished. The agent `design-build` of the plugin (`laminar:design-build`, in Claude Code) runs it, because a workflow runs no command: it compiles the code and runs the test files of the test steps of the finished groups, by its own body. It writes the output into `<results>/plans/<n>/build/build-groups-<groups of the call>-<k>.txt`. It takes the commands from the argument `buildCommands`, `{compile, test}`, where the calling session gives them. It runs no test outside those test files, so the session runs the whole suite (SKILL.md, section 5).

Each failure goes to each group of the call whose writer returned its file, else to each group whose step lists it, else to each group whose test file has the base name that the failure names, such as its test class. Each finished group with a failure then gets 1 fix call of its writer, in the order of the group numbers, with the line `Build failures:`, and the build runs again; the argument `buildFixPasses`, default 1 and at most 3, counts these passes. A failure that reaches no finished group of the call, such as a failure in a file of no group, a run where no test ran, or a failure of a group that stopped, gets no fix call, and every finished group fails with it. After the last build, a finished group gets `build.result` `passed` only where the compile passed and no failure of its own or of every group stands. A group whose failure stands comes back stopped with `tests-failed` for a failing test, else `build-failed`, with the failures in `buildFailures`, its own first. A group that builds on such a group of the call comes back stopped with the same stop and `waits on group <n>`. Where the compile failed in another group only, a group comes back stopped with `build-failed`, because none of its tests ran. Where the build of the round did not run, each group keeps `build.result` `not run`, and `roundBuild.notRun` gives the reason. A commit of 1 group of the round may not build alone, because only the build of the round checks the groups.
