# The design check and the migration script

Contents: 1. The marks and the exit codes · 2. The zone order · 3. The cycle check · 4. The other checks · 5. The migration script

This file says what the design check, `scripts/checkDesign.mjs`, reports on the design model, and how the migration script, `scripts/planMigration.mjs`, orders its steps. `design-model.md` holds the form of the model, and the key tables of `design-decisions.md`, `design-boundaries.md` and `design-findings.md` name the check of each key.

## 1. The marks and the exit codes

The design check marks each line it prints `defect`, `recheck` or `found-wrong`, and exits with 1 where a `defect` or a `recheck` line stands; a `found-wrong` line, a recheck case that `decisions.scriptCases` lists, does not set exit 1. Each such line has the form `<mark><TAB><code><TAB><display name><TAB><text>`, with no JSON path, so an object of `decisions.scriptCases` can name the 1 line it clears (`design-findings.md`, `scriptCases`). An object of `scriptCases` that matches no line prints as `not matched<TAB><code><TAB><display name><TAB><text>`. With `--shape-review`, the last head line starts with `shape reviews:`. A value outside a closed list, a wrong type or a malformed model stops the check with exit 2, the JSON path and the value. It reports as a defect a method of a changed class with no `body` whose `calls` name 2 or more parts or name an exit. The designer rechecks each recheck case against the model.

With `--repo`, the design check and the migration script read the current tree as the tree of 1 commit: the commit that `--tree <commit>` names, else the plan commit that `plan-commit.txt` holds where that file stands in the folder of the model, else the commit of `base-commit.txt`, which a results folder of 0.72.0 holds as the current tree. They read that tree with `git show <commit>:<path>` and `git ls-tree`, and never the working tree, because after a writer the working tree holds the files of that writer, and a check on them would read the change as the current tree. Where no flag and no file exists, they read the working tree. The design check reads a line older than the change, a cause line of an item of a shape run left `outside the change` or an edge of a folder cycle left so, in the base commit, which `--base <commit>` or `base-commit.txt` names, where it differs from the commit of the current tree. A failed git command stops either script with exit 2. The head line of the migration script starts with `Current tree:` and names the commit.

The design check prints 2 more head lines. The line that starts with `response types:` names each response `type` that names no class of the model, as a library type that it did not check. The line that starts with `exit list check:` says which paths the check of unlisted exits read and which it printed as not checked; an exit class there is the class of an exit that `exits` lists and that another method runs, or a class that an integration test substitutes.

The designer runs the design check twice: on the pass-1 model, before the first shape check, and on the whole model after pass 2 (`design-model.md`, section 2). On the pass-1 model it prints the keys of pass 2 as missing, and the designer fixes every other line, because the check costs no agent call and finds data-flow and completeness defects that would cost a shape run.

## 2. The zone order

This section describes the zone order. A zone order applies where `decisions.conventions.zoneOrder` names a conventions file. The default zone order below applies only under a layout module, which has the backend folder layout it describes. A layout module is a folder of the scope that holds a folder named `in`, `api`, `spi` or `out`; a folder named `domain` does not count, because that name is common outside the layout. A folder of the scope is each folder of `folders` and each folder in the `file` of a class, at every depth of its path. Where no conventions file names a zone order and no folder of the scope has the layout, `zone` is optional, the cycle check runs with no order and reports cycles only, and its first line is `zone order: not applied, no conventions file, and no folder of the scope has the backend layout of an api, spi, in or out folder`. Where the default zone order applies to 1 or more layout modules, the cycle check prints 1 line `zone order: not applied to <folder>` for each folder of a class outside a layout module, and checks no relation of such a class against the order. A `zone` given where no order applies is ignored, and the check prints `zone: ignored on <N> classes, because no zone order applies`.

A project states its own zone order in its conventions file, inside 1 fenced block whose info string is `zones`, with 1 allowed relation per line in 1 of these forms: `<zone> calls <zone>`, `<zone> implements <zone>` or `<zone> calls <zone> of another module`. The design check reads only that block, so a sentence of the file never counts as a relation. The design check takes no other line of the block as a relation, such as `<zone> implements <zone> of another module`. The cycle check names each such line that is not blank in 1 head line `zone order: line not read: <line>`. The default zone order of the design skill, in the form a project writes it, is:

```zones
in calls api
domain implements api
domain calls spi
out implements spi
api calls domain
spi calls domain
out calls domain
out calls in of another module
```

A relation `<zone> calls <zone> of another module` allows the call only where the 2 classes are in 2 different modules, and a call between the same 2 zones inside 1 module stays a relation the order does not allow. The module of a class is the deepest folder above its `file` that holds a folder named `in` or `out` and lies inside no folder named `in` or `out`, because the book wraps the whole module in these 2 folders: "Applying encapsulation to each part gives `app/` for the application, `in/` for everything that uses it, and `out/` for everything the application needs." (*The Principles at Every Scale*, *Hexagonal Architecture*) A folder named `api` or `spi` does not tell 2 modules apart, because the book puts these folders inside `app/`. A folder inside `in` or `out`, such as `api` in `order/in/api/`, belongs to the module that holds that `in` or `out` folder. Where either class has no module, as in a tree with a zone order of a conventions file and no `in` or `out` folder, the design check cannot tell the modules apart and never allows a relation `of another module`. The book lets 1 module reach another through the `out` folder of the caller and the `in` folder of the module it calls: "When the order module reaches the consignment module, the call leaves through the `out/modules/` folder of order and arrives at the `in/modules/` folder of consignment." (*The Principles at Every Scale*, *Hexagonal Architecture*) An `out` class that calls the `in` class of its own module follows no path that the book shows, so the default zone order does not allow it.

A class may always call a class of its own zone. The type of a field counts as a call of its zone. A relation `<zone> implements <zone>` also allows the calls and the field types into the zone it implements, because a decorator in `out` that holds an `spi` interface, or in `domain` around an `api` interface, is a legal design; but the cycle check prints each such call as a recheck case (`call-into-the-implemented-zone`), because a use case that reaches another use case through its `api` is a cycle, and the designer records a decorator in 1 line under `scriptCases`. The zones and the zone order are words of this skill, not of the book.

## 3. The cycle check

The cycle check reads `zone`, the field types, `calls`, `implements` and `extends` for the edges between classes, and no parameter or return type there. Its first line says which edges it had, which edges the graph of folders adds, and whether a zone order applies, so a silent check never reads as a pass. It reports each cycle between classes as its path (`cycle`). The graph of classes reads a nested class, such as `Rental.Period`, as the class of the same file that its first name piece names, such as `Rental`, so 2 types of 1 file make no cycle, and a cycle through a nested class of another file stays a cycle between the 2 outer classes. The zone check skips each class of a test file, as the check of the current classes in section 4 reads a test file, because a substitute in a test stands outside the zone order of production. Where a zone order applies, it also reports each relation the order does not allow as a recheck case (`zone-order-broken`), and a zone that the order does not name once, as a recheck case (`zone-outside-the-order`), and skips its relations; it skips each relation of a class with no `zone` too, and counts both as the edges of a class with no zone or a zone outside the order on its first line.

It also builds the graph of folders from the same edges, and adds the parameter and return types of the public members, because a type that a public signature names is what an import of the file shows: an edge between 2 classes of 2 folders is an edge between the 2 folders, where the folder of a class is the folder of its `file`. The zone check of the classes keeps its own edges, with no parameter or return type. It reports each cycle between folders as its path of folders, as a recheck case (`folder-cycle`); a cycle whose edges stand in the base commit takes `outside the change` under `scriptCases` (`design-findings.md`, `scriptCases`). The book: "Every folder, at any depth, stays consistent inside and hides its contents behind its name, which introduces a new abstraction level." (*The Principles at Every Scale*, *Modular Monolith*) 2 folders that need each other are 1 part in 2 folders, or miss a boundary between them.

## 4. The other checks

- The data-flow check reads each method with a `body` and each path from an entry to its exits, where every parameter of a called part must be a parameter of the caller, a field of its class or the result of an earlier call of the same body. A value counts as provided where its root name, before the first dot or call, is one of these, so `request.customerId()` is provided by the parameter `request`; the same holds for the check by the signature below. A value counts as declared by an assignment, a loop head, a catch clause, a resource of a try or a pattern of `instanceof` or `case`, and the text inside quotes is no code; a call counts as resolved where the class, a supertype of the model, the root object of the language or a Java enum holds the member, or where a supertype is no class of the model, because a library type may hold the member. A method on such a path with no `body` and exactly 1 name in `calls` is checked by its signature, where each parameter of the called member must be a parameter of the method or a field of its class, and gives 1 recheck case per missing value (`data-source-missing`). Any other method on such a path with no `body` is a recheck case (`path-step-without-body`), because its data flow is not checked. It reads Java, JavaScript and TypeScript, and its word lists cover only these 3 languages, so it prints a body or a path step in another language as not checked, never as a defect.
- The exit checks report a class whose `does` is `computes` and whose `calls` reach an exit, an exit reached from 2 classes in 2 zones, and an exit that its `from` method does not reach (`design-boundaries.md`, `exits`). They report an exit whose `failed` names no type (`exit-failure-unnamed`), and print it as not checked where the framework answers it and an entry that reaches it lists that response. They report an exit whose `handledAt` method has no parameter of the type that `failed` names, or of a supertype that the model lists through `extends` (`handler-takes-other-type`), and an exit whose `handledAt` is `framework` where an entry whose path reaches its `from` method lists no response whose `handledAt` is `framework` (`framework-response-unlisted`). They report each exit that the data-flow check finds on the path of an entry whose `changed` is true and that `exits` does not list, as a recheck case (`exit-unlisted`), and print a path in a language the data-flow check does not read as not checked (`design-boundaries.md`, `exits`).
- The response checks report a response whose `type` is the word `framework`, because `framework` is a word of a handler and not a type (`framework-as-response-type`), and an entry whose `handler` is `framework` that lists no response whose `handledAt` is `framework` (`framework-handler-response-unlisted`). They print each `type` that names no class of the model as `library type, not checked` (`design-boundaries.md`, `entries`).
- The check of the current classes (`current-class-unaccounted`, `design-model.md`, section 4) reads a test file as 1 that stands under a folder `test`, `tests`, `__tests__` or `spec`, that is named like `FooTest`, or with `.test.` or `_test`, or that `decisions.tests` names; it accounts each private, nested or unexported helper type of such a file to its test.
- The check of the tried names reads the names that each class of the model held before: its `oldName`, the rename between rounds of each pair of the round models that the round script keeps under `rounds/<n>/design-model.json` beside the model, and between the model of the last round and the model, and between each 2 shape runs of `--shape-review` in the order of their numbers, by the classes of the shape model that the prepare command saves as `shape-model.json` beside each `review.md`, or by those of `review-abstractions.json` for a run folder without it. It pairs a class of 1 shape run with a class of the next shape run as the round script pairs a rename between rounds: a class gone with exactly 1 added class of the same file or the same method names. Where a class of the model holds its second name or a later one, and the last shape run that judged it keeps a prediction failure on it, the check reports a recheck case (`renamed-class-raised-again`), because the grouping can be wrong (`designing.md`, section 6), and because a second rename can also be right, such as a rename that only drops a word that the path already says (`designing.md`, section 5). A rename that moves the file and changes the methods at once is not paired, so the check does not see it; in a run folder without `shape-model.json`, a method with no body is no child of its class in `review-abstractions.json`, so the pairing by method names reads only the methods with a body; a class that 2 files of the model name is not followed across rounds; and a shape run whose folder holds no `review-abstractions.json` adds no pair.
- The check of the renames without a finding reads the same pairs, of classes, methods and fields: between each 2 shape runs, by `listRenamesBetweenRounds` on the 2 saved shape models, or by the class pairs of `review-abstractions.json` where 1 of them has none; between the last shape run and the model; between each 2 round models and between the last round and the model; and each `oldName` of the model, only with `--review`. A method whose class only changed its name keeps its own name and makes no pair. It reports each pair whose old name no item of the run folder, no item of a shape run and no object of the decided list names, and whose old file stands in no folder that a module item names, as a recheck case (`renamed-without-finding`), with the old name, the new name and where the rename happened, and asks for 1 line on why the new name is better. A round renames a name that carries no finding only where the new name is better, so the designer answers the case under `scriptCases` with that 1 line as its `reason`.
- The check of the simplest form reports 2 recheck cases on a class of a `created` file. The first is a type whose only field is a list, a map, a set or an array of the language, that extends and implements no type, and none of whose method bodies holds a condition, a loop or a second statement (`type-holds-only-a-collection`). The second is an interface that exactly 1 class of the model implements, that stands in no `api` or `spi` zone or folder, and that no owner names, as its `owner` or in the `shape` of its `depth`, where the user or a forecast took that depth (`interface-with-one-implementation`). The designer answers each under `scriptCases` where the larger form holds, by `designing.md`, section 7; the check reads only the classes of the model, so an implementation that only the current tree or a test holds does not count.
- The check of an owner without its values reports each owner of `decisions.owners` that is a method with no `body` and no `calls`, not marked `unchanged`, that returns a value, that is new, and that takes 1 or more parameters whose inputs are all keys, as a recheck case (`owner-without-its-values`), because a writer then copies the values from another class or makes them up. A method is new where its class stands in a `created` file, or, with `--repo`, where the current file of its class does not hold its signature. An input is a key where its type is a number, a text, a boolean or a closed set; a closed set is a class of the model whose `kindWord` is `enum`, or, with `--repo`, a type that a file of the current tree declares as an enum of Java, Kotlin or TypeScript, as a class of Python that extends an `Enum`, or as a frozen object of JavaScript whose keys are upper-case constants. It reads only an owner method with at least 1 parameter, because a method with no parameter reads the state of its object. A method that uses a member other than a field whose type is a closed set has an input that can carry the values. With `--repo`, the case names the first file of the current tree that the model names and that holds a table of literal values keyed by the closed set of a parameter. The designer names the input that carries the values, makes the class that holds them the owner, or writes them as the body of the owner (`design-model.md`, section 1), and answers the case under `scriptCases` where a source that the model does not show gives them, such as a setting of a framework or a sentence of the decision. The check cannot see a parameter whose type can carry the values but does not, such as a member that holds the tier and not the limit, a source that a field of a library type gives, or a closed set of a library; it reads only owners that are methods.
- The check of a repeated table reads the literal tables of each `body` of a class of the model outside a test file, and, with `--repo`, of each file of the current tree that the model names as an `unchanged`, `modified` or `moved` child of a folder or as the file of such a class, by its `oldPath` where it moved; it leaves out a test file, and a table whose declared name stands in `removed` of a class of that file or in `removedClasses` of its child, because the model moves it. A literal table is a keyed table or a literal set, read after the comments are left out and with the text inside quotes read as 1 string, so a number of a message or of a comment counts for nothing. A keyed table holds 2 or more entries whose keys are constants of 1 closed set, each with a literal value: `[E.K]: v` of JavaScript and TypeScript, `Map.of(E.K, v)`, `Map.entry(E.K, v)` and `put(E.K, v)` of Java, `E.K to v` and `E.K -> v` of Kotlin, `E.K: v` of a Python dict, `[E.K, v]` of a JavaScript `Map`, and the arms of 1 switch, `case K -> v`, `case E.K -> v` or `case K: return v`. A literal set holds 2 or more literals of 1 kind and nothing else, all numbers other than 0, 1 and -1, or all strings. It reports a body whose table another body of the model, or a file of the current tree that is not the file of its own class, holds again as a recheck case (`repeated-table`): 2 keyed tables of 1 closed set with 2 or more shared keys and the same value on each, or 2 equal literal sets. The designer makes 1 of the 2 the owner of the decision, or answers the case under `scriptCases` where they are 2 rules that hold the same values today, because whether 2 equal tables are 1 rule or 2 is a question of the business. A clean check does not mean that no decision is written twice, because the check cannot see: a table in a file that the model names in no folder and no class; a decision written as conditions, as a chain of conditional expressions, or built in a loop; a table in a configuration file, a database or an environment variable; values that differ by unit or form, such as 23 kilograms and 23000 grams, or a table keyed by strings in 1 place and by a closed set in the other; the same keys with other values, such as a rule changed in 1 place only; a single value written twice; a table in a language other than Java, Kotlin, JavaScript, TypeScript and Python; and a decision that the model writes in no body, which the check of an owner without its values reads.
- The group check reports a `group` on a class of an `unchanged` file (`group-on-unchanged-class`, `design-model.md`, section 3).
- The test check reports a unit test of a class whose `does` is `coordinates` (`design-boundaries.md`, `tests`).
- The field check reports each field with no `type` in a class of a `created` file, except the constants of an enum (`field-without-type`, `design-model.md`, section 3). With `--repo`, it reports each field that a Java, JavaScript or TypeScript file of the current tree declares in a class of a `modified` file and that the model does not list (`field-unlisted`), and prints a class in another language as not checked; a head line that starts with `field check:` names the languages it did not check. With `--repo`, it also reports each public method that a Java, JavaScript or TypeScript file of the current tree declares in a class of a `modified` file outside a test file and that the model lists neither under `methods`, by its `name` or its `oldName`, nor under `removed` (`method-unlisted`), because a writer reads a public method that the model leaves out as removed and removes its tests; it reads a getter or a setter of a script as a field, and a record lists its accessors under `fields`. A head line that starts with `method check:` names each class it did not check, by its language or because its current file declares no such class, so a class the check cannot read is never a silent pass.
- With `--repo`, the check of an unchanged member reads the current tree for each object of `decisions.findings` of a shape run whose `reason` is `outside the change` (`outside-the-change-but-changed`), for each object of `entries` whose `changed` is false (`entry-changed-but-marked-unchanged`), and for each method marked `unchanged: true` (`method-changed-but-marked-unchanged`) (`design-findings.md`, `findings`; `design-boundaries.md`, `entries`; `design-model.md`, section 3).

## 5. The migration script

The migration script reads `decisions.tests` for its test steps, `decisions.existingDefects` for the groups of the existing defects and `decisions.stops` for the stopped groups of a cut plan, and no other key of `decisions`. It reads `group` on each class and writes its steps per migration group, in the order of the group numbers, and inside each group in 7 migration stages: folders, moves and renames, created classes, changed members, bodies, removals, and then tests. The designer sets `group` by the boundary the classes share: an abstraction, a folder or a decision, and the narrower one where 2 fit, so the abstraction comes before its folder and the folder before the decision. The code builds and its tests pass at the end of each migration group, not after each step, because a changed member changes a signature before the bodies of its callers. The script reorders no group: it prints a `defect` line for each step of a group that names a class or a file that a step of a later group creates (`group-order-broken`), lists each such defect in the section `## Defects of the order` of `migration.md`, and exits with 1, and the designer changes the `group` numbers. A class with no `group` is in group 1, so the same check covers it. A group of `decisions.existingDefects` stands apart, with its own label (`design-findings.md`, `existingDefects`). A method marked `unchanged: true` gets no body step. A unit test joins the group of its class, so a class of an `unchanged` file never needs a `group`. An integration test joins the first group at whose end the whole path of its entry exists, so it joins the group of the behavior it tests where a later group only changes what stands behind an interface. The path ends at each exit that a substitute of the test replaces. At an interface of that group or an earlier one, where the tree or that group holds an implementation of it, the path follows only the implementations of that group and of earlier groups, and the test runs against an implementation that a later group changes or removes in its current form. Where no implementation exists at the end of a group, such as a new interface whose only implementation a later group creates, the path follows every implementation, so the test waits for that later group. Where the test runs against such an implementation, its step adds `; in this group the tests run against <implementations> as <interface>`. In each later group that creates or changes an implementation of that interface, the script writes 1 more step in the migration stage tests: `runs again the integration tests of <entry>, written in group <g>, against <implementation>; they must pass unchanged: <tests>`. Where that group removes the implementation the tests ran against and the test file of the tree names it, the step is `changes the integration tests of <entry>, written in group <g>, to run against <implementation> in place of <removed implementations>: <tests>`; where the test file names none of them, the step stays the step that runs the tests again unchanged; and where the tree does not show the test file, with no `--repo` or for a new test file, the step is `runs again the integration tests of <entry>, written in group <g>, against <implementation> in place of <removed implementations>; change only the lines that name the removed implementation: <tests>`. The script reads a name of a removed implementation as the name its class has in the tree. A path that reaches a later group by a direct call, and not through an interface, still sends the test to that group. With `--findings <findings.json>`, the script writes 1 finding step per entry that holds no reason class, `fixes finding <number>: <check> on <display name>`, in the migration stage bodies, or tests for a finding on test code, in the group of the class of the finding, under the name the model gives the abstraction. An entry that the decided list decides, an entry with `fixedBy`, which a finished group of the plan before already fixed, an entry with `toConsider`, which is an item to consider, and an entry whose abstraction the model removes each get no step and 1 line under `## Findings with no step` at the end of `migration.md`, with the why `decided by <decidedBy>: <reason>`, `fixed by plan <n> group <g>`, `to consider` or `the model removes <display name or file>`. An entry with no group is the defect `finding-without-group`, and an entry on a method marked `unchanged: true` is the defect `finding-on-unchanged-method`, because its step would change a method that the model keeps. A later plan is cut by `--classes <display names>`, also an empty one: the script plans only the migration groups of the classes the designer changed, with the test steps of their changed signatures, of the finding steps, of a changed test against the model of `--before` and of a stop of the plan before `--plan <n>`, every step of a stopped group, and each group keeps its number; the head line `Planned groups:` names them (`design-rounds.md`, section 8).

- A changed public member breaks each reader file, so with `--repo` the step of the change lists each reader file and updates it in the group of the change, which then builds alone: a rename of a field by `oldName`, `renames <Class>#<old> to <new>, with no change of behavior; updates the files that read it: <files>`; a rename of a method by `oldName` where the current file declares the old name with other parameters or another return type, `renames <Class>#<old> to <new> and changes its signature to that of the model; updates the files that read it: <files>`; a removal, `removes <names> from <Class>, once no caller uses them; updates the files that read it: <files>`; and a method whose parameters or return type change with no rename, in the step of changed members, `; updates the callers of the changed signatures in <files>`. A reader file is a file of the tree that names the class and the member, or the file of a class of the model whose body reads the member, whose `calls` name it, or that implements or extends the class. A file that the model removes in a later group is still a reader file, because it exists until that group, and the step names it with `, which group <n> removes`; the same holds for a test file of a test step and for a file whose imports a step updates. Where a reader file of a changed signature, or a test file of its test step, holds a changed class of the model of a later group, the step names it with ` (change only the lines that the new signature breaks; the rest of this class is group <n>)`, and the rename step of that later group for the same method adds `; group <g> already changed the lines that the new signature breaks`; no class moves to another group. A nested class is searched by every piece of its dotted name, through its outermost type, so a file that holds only its inner name is no reader file.

- In the group of each `modified` class whose public signature changes, its constructor and a field renamed by `oldName` included, the script searches the tree for test files that hold the name of the class, for Java, JavaScript, TypeScript and Kotlin with `--repo`. Where the search finds 1 or more files, it writes 1 step in the migration stage tests: `updates or removes the tests that construct or call <Class>: <files>`; where the search finds none, it writes no step. For a language outside these 4, or with no `--repo`, the step ends with `tests not found, language not read`, so the writer looks. A class that the change creates inside a `modified` file gets no such step. A test case that a designed test of the group covers is removed and not kept, so the step adds no copy of a test.
- A class that the model removes, the class of a `removed` file or a name of `removedClasses`, breaks each existing test that names it. So with `--repo`, in the group of the removal, the script writes 1 step in the migration stage tests for each such class that a test file of the tree names: `updates or removes the tests that read <Class>, which this group removes: <files>`. Where a test of `decisions.tests` in a later group writes the same file, the step names the file with ` (remove or change only the tests that read it; group <n> writes the tests of this file)`, so the group of the removal builds and the later group writes the new tests. A test that names only a library that the change removes, and no class of the model, is not found.
- In the group of each `modified` class whose path now reaches a new outside call, an exit whose class the change creates or whose method the current file of its class does not hold, the script writes 1 step in the migration stage tests, also where the signature of the class stays: `updates the tests that reach <outside interfaces> through <Class>: <files>`. The files are the test files that hold the name of the class or of a class of the model whose path reaches it, such as the controller of its entry. Where the search finds none, the step names the entries whose path reaches the class, because a test that runs an entry by its route names no class: `no test file names it or a caller of it; find the tests of <entries> by hand`. For a language outside the 4, or with no `--repo`, the step ends with `tests not found, language not read`.
- A created folder is a step of the migration stage folders alone, and never a step of the migration stage created classes.
- A modified file of framework wiring, such as an XML file, holds no class that the model can state, so the script writes 1 step for it in the migration stage bodies: `not modelled: edit <path> by hand (framework wiring)`. The step joins the lowest migration group of the classes whose `file` stands under the folder of that file, and group 1 where no class does.
- A step of the migration stage created classes writes the class with the bodies of its methods in the same step, as `creates <file> with <classes> and the bodies of <methods>`, because a file of signatures alone does not compile in every language. The migration stage bodies holds only the bodies of methods of `modified` classes; the migration stages are an order of work, not points where the code builds.
- A `removed` child whose code moved, which is the old file that the `oldPath` of a `created` child names, joins the migration group of that created class, and its removal step, `removes the file <old>, whose code <new> now holds`, comes right after the step of that class in the same group, so no group ends with 2 copies of 1 class.
- With `--repo`, the script finds the current callers of each renamed or moved name in the tree, and writes a body step for a method of a `modified` class whose signature differs from the current tree. Each step of a moved file, of a renamed class and of a class created with `oldPath` also lists the files that import the class, and ends with `; updates the imports of <files>`, because such a class does not build in a language that imports by package until its callers import it by its new name and place.
