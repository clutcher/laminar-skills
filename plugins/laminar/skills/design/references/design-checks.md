# The design check and the migration script

Contents: 1. The marks and the exit codes · 2. The zone order · 3. The cycle check · 4. The other checks · 5. The migration script

This file says what the design check, `scripts/checkDesign.mjs`, reports on the design model, and how the migration script, `scripts/planMigration.mjs`, orders its steps. `design-model.md` holds the form of the model, and the key tables of `design-decisions.md`, `design-boundaries.md` and `design-findings.md` name the check of each key.

## 1. The marks and the exit codes

The design check marks each line it prints `defect`, `recheck` or `found-wrong`, and exits with 1 where a `defect` or a `recheck` line stands; a `found-wrong` line, a recheck case that `decisions.scriptCases` lists, does not set exit 1. Each such line has the form `<mark><TAB><code><TAB><display name><TAB><text>`, with no JSON path, so an object of `decisions.scriptCases` can name the 1 line it clears (`design-findings.md`, `scriptCases`). An object of `scriptCases` that matches no line prints as `not matched<TAB><code><TAB><display name><TAB><text>`. With `--shape-review`, the last head line starts with `shape reviews:`. A value outside a closed list, a wrong type or a malformed model stops the check with exit 2, the JSON path and the value. It reports as a defect a method of a changed class with no `body` whose `calls` name 2 or more parts or name an exit. The designer rechecks each recheck case against the model.

With `--repo`, the design check and the migration script read the current tree as the tree of 1 commit: the commit that `--tree <commit>` names, else the plan commit that `plan-commit.txt` holds where that file stands in the folder of the model, else the commit of `base-commit.txt`, which a results folder of 0.72.0 holds as the current tree. They read that tree with `git show <commit>:<path>` and `git ls-tree`, and never the working tree, because after a writer the working tree holds the files of that writer, and a check on them would read the change as the current tree. Where no flag and no file exists, they read the working tree. The design check reads a line older than the change, a cause line of an item of a shape run left `outside the change` or an edge of a folder cycle left so, in the base commit, which `--base <commit>` or `base-commit.txt` names, where it differs from the commit of the current tree. A failed git command stops either script with exit 2. The head line of the migration script starts with `Current tree:` and names the commit.

The design check prints 2 more head lines. The line that starts with `response types:` names each response `type` that names no class of the model, as a library type that it did not check. The line that starts with `exit list check:` says which paths the check of unlisted exits read and which it printed as not checked; an exit class there is the class of an exit that `exits` lists and that another method runs, or a class that an integration test substitutes.

The designer runs the design check twice: on the pass-1 model, before the first shape check, and on the whole model after pass 2 (`design-model.md`, section 2). On the pass-1 model it prints the keys of pass 2 as missing, and the designer fixes every other line, because the check costs no agent call and finds data-flow and completeness defects that would cost a shape run.

## 2. The zone order

This section describes the zone order. A zone order applies where `decisions.conventions.zoneOrder` names a conventions file. The default zone order below applies only under a module with the backend folder layout it describes. Such a module is a folder of the scope that holds a folder named `in`, `api`, `spi` or `out`; a folder named `domain` does not count, because that name is common outside the layout. A folder of the scope is each folder of `folders` and each folder in the `file` of a class, at every depth of its path. Where no conventions file names a zone order and no folder of the scope has the layout, `zone` is optional, the cycle check runs with no order and reports cycles only, and its first line is `zone order: not applied, no conventions file, and no folder of the scope has the backend layout of an api, spi, in or out folder`. Where the default zone order applies to 1 or more modules, the cycle check prints 1 line `zone order: not applied to <folder>` for each folder of a class outside such a module, and checks no relation of such a class against the order. A `zone` given where no order applies is ignored, and the check prints `zone: ignored on <N> classes, because no zone order applies`.

A project states its own zone order in its conventions file, inside 1 fenced block whose info string is `zones`, with 1 allowed relation per line in 1 of 2 forms: `<zone> calls <zone>` or `<zone> implements <zone>`. The design check reads only that block, so a sentence of the file never counts as a relation. Where the order is the book's layout, the default order, in the form a project writes it, has nothing that calls `in`:

```zones
in calls api
domain implements api
domain calls spi
out implements spi
api calls domain
spi calls domain
out calls domain
```

A class may always call a class of its own zone. The type of a field counts as a call of its zone. A relation `<zone> implements <zone>` also allows the calls and the field types into the zone it implements, because a decorator in `out` that holds an `spi` interface, or in `domain` around an `api` interface, is a legal design; but the cycle check prints each such call as a recheck case (`call-into-the-implemented-zone`), because a use case that reaches another use case through its `api` is a cycle, and the designer records a decorator in 1 line under `scriptCases`. The zones and the zone order are words of this skill, not of the book.

## 3. The cycle check

The cycle check reads `zone`, the field types, `calls`, `implements` and `extends` for the edges between classes, and no parameter or return type there. Its first line says which edges it had, which edges the graph of folders adds, and whether a zone order applies, so a silent check never reads as a pass. It reports each cycle between classes as its path (`cycle`). Where a zone order applies, it also reports each relation the order does not allow as a recheck case (`zone-order-broken`), and a zone that the order does not name once, as a recheck case (`zone-outside-the-order`), and skips its relations; it skips each relation of a class with no `zone` too, and counts both as the edges of a class with no zone or a zone outside the order on its first line.

It also builds the graph of folders from the same edges, and adds the parameter and return types of the public members, because a type that a public signature names is what an import of the file shows: an edge between 2 classes of 2 folders is an edge between the 2 folders, where the folder of a class is the folder of its `file`. The zone check of the classes keeps its own edges, with no parameter or return type. It reports each cycle between folders as its path of folders, as a recheck case (`folder-cycle`); a cycle whose edges stand in the base commit takes `outside the change` under `scriptCases` (`design-findings.md`, `scriptCases`). The book: "Every folder, at any depth, stays consistent inside and hides its contents behind its name, which introduces a new abstraction level." (*The Principles at Every Scale*, *Modular Monolith*) 2 folders that need each other are 1 part in 2 folders, or miss a boundary between them.

## 4. The other checks

- The data-flow check reads each method with a `body` and each path from an entry to its exits, where every parameter of a called part must be a parameter of the caller, a field of its class or the result of an earlier call of the same body. A value counts as provided where its root name, before the first dot or call, is one of these, so `request.customerId()` is provided by the parameter `request`; the same holds for the check by the signature below. A method on such a path with no `body` and exactly 1 name in `calls` is checked by its signature, where each parameter of the called member must be a parameter of the method or a field of its class, and gives 1 recheck case per missing value (`data-source-missing`). Any other method on such a path with no `body` is a recheck case (`path-step-without-body`), because its data flow is not checked. It reads Java, JavaScript and TypeScript, and its word lists cover only these 3 languages, so it prints a body or a path step in another language as not checked, never as a defect.
- The exit checks report a class whose `does` is `computes` and whose `calls` reach an exit, an exit reached from 2 classes in 2 zones, and an exit that its `from` method does not reach (`design-boundaries.md`, `exits`). They report an exit whose `failed` names no type (`exit-failure-unnamed`), and print it as not checked where the framework answers it and an entry that reaches it lists that response. They report an exit whose `handledAt` method has no parameter of the type that `failed` names, or of a supertype that the model lists through `extends` (`handler-takes-other-type`), and an exit whose `handledAt` is `framework` where an entry whose path reaches its `from` method lists no response whose `handledAt` is `framework` (`framework-response-unlisted`). They report each exit that the data-flow check finds on the path of an entry whose `changed` is true and that `exits` does not list, as a recheck case (`exit-unlisted`), and print a path in a language the data-flow check does not read as not checked (`design-boundaries.md`, `exits`).
- The response checks report a response whose `type` is the word `framework`, because `framework` is a word of a handler and not a type (`framework-as-response-type`), and an entry whose `handler` is `framework` that lists no response whose `handledAt` is `framework` (`framework-handler-response-unlisted`). They print each `type` that names no class of the model as `library type, not checked` (`design-boundaries.md`, `entries`).
- The check of the current classes (`current-class-unaccounted`, `design-model.md`, section 4) reads a test file as 1 that stands under a folder `test`, `tests`, `__tests__` or `spec`, that is named like `FooTest`, or with `.test.` or `_test`, or that `decisions.tests` names; it accounts each private, nested or unexported helper type of such a file to its test.
- The group check reports a `group` on a class of an `unchanged` file (`group-on-unchanged-class`, `design-model.md`, section 3).
- The test check reports a unit test of a class whose `does` is `coordinates` (`design-boundaries.md`, `tests`).
- The field check reports each field with no `type` in a class of a `created` file, except the constants of an enum (`field-without-type`, `design-model.md`, section 3). With `--repo`, it reports each field that a Java, JavaScript or TypeScript file of the current tree declares in a class of a `modified` file and that the model does not list (`field-unlisted`), and prints a class in another language as not checked; a head line that starts with `field check:` names the languages it did not check.
- With `--repo`, the check of an unchanged member reads the current tree for each object of `decisions.findings` of a shape run whose `reason` is `outside the change` (`outside-the-change-but-changed`), for each object of `entries` whose `changed` is false (`entry-changed-but-marked-unchanged`), and for each method marked `unchanged: true` (`method-changed-but-marked-unchanged`) (`design-findings.md`, `findings`; `design-boundaries.md`, `entries`; `design-model.md`, section 3).

## 5. The migration script

The migration script reads `decisions.tests` for its test steps, `decisions.existingDefects` for the groups of the existing defects and `decisions.stops` for the stopped groups of a cut plan, and no other key of `decisions`. It reads `group` on each class and writes its steps per migration group, in the order of the group numbers, and inside each group in 7 migration stages: folders, moves and renames, created classes, changed members, bodies, removals, and then tests. The designer sets `group` by the boundary the classes share: an abstraction, a folder or a decision, and the narrower one where 2 fit, so the abstraction comes before its folder and the folder before the decision. The code builds and its tests pass at the end of each migration group, not after each step, because a changed member changes a signature before the bodies of its callers. The script reorders no group: it prints a `defect` line for each step of a group that names a class or a file that a step of a later group creates (`group-order-broken`), lists each such defect in the section `## Defects of the order` of `migration.md`, and exits with 1, and the designer changes the `group` numbers. A class with no `group` is in group 1, so the same check covers it. A group of `decisions.existingDefects` stands apart, with its own label (`design-findings.md`, `existingDefects`). A method marked `unchanged: true` gets no body step. An integration test joins the highest group of the classes that the path of its entry names, and a unit test joins the group of its class, so a class of an `unchanged` file never needs a `group`. With `--findings <findings.json>`, the script writes 1 finding step per entry that holds no reason class, `fixes finding <number>: <check> on <display name>`, in the migration stage bodies, or tests for a finding on test code, in the group of the class of the finding, under the name the model gives the abstraction. An entry that the decided list decides, an entry with `fixedBy`, which a finished group of the plan before already fixed, an entry with `toConsider`, which is an item to consider, and an entry whose abstraction the model removes each get no step and 1 line under `## Findings with no step` at the end of `migration.md`, with the why `decided by <decidedBy>: <reason>`, `fixed by plan <n> group <g>`, `to consider` or `the model removes <display name or file>`. An entry with no group is the defect `finding-without-group`, and an entry on a method marked `unchanged: true` is the defect `finding-on-unchanged-method`, because its step would change a method that the model keeps. A later plan is cut by `--classes <display names>`, also an empty one: the script plans only the migration groups of the classes the designer changed, with the test steps of their changed signatures, of the finding steps, of a changed test against the model of `--before` and of a stop of the plan before `--plan <n>`, every step of a stopped group, and each group keeps its number; the head line `Planned groups:` names them (`design-rounds.md`, section 8).

- A changed public member breaks each reader file, so with `--repo` the step of the change lists each reader file and updates it in the group of the change, which then builds alone: a rename of a field by `oldName`, `renames <Class>#<old> to <new>, with no change of behavior; updates the files that read it: <files>`; a removal, `removes <names> from <Class>, once no caller uses them; updates the files that read it: <files>`; and a method whose signature changes with no rename, in the step of changed members, `; updates the callers of the changed signatures in <files>`. A reader file is a file of the tree that names the class and the member, or the file of a class of the model whose body reads the member. A nested class is searched by every piece of its dotted name, through its outermost type, so a file that holds only its inner name is no reader file.

- In the group of each `modified` class whose public signature changes, its constructor and a field renamed by `oldName` included, the script searches the tree for test files that hold the name of the class, for Java, JavaScript, TypeScript and Kotlin with `--repo`. Where the search finds 1 or more files, it writes 1 step in the migration stage tests: `updates or removes the tests that construct or call <Class>: <files>`; where the search finds none, it writes no step. For a language outside these 4, or with no `--repo`, the step ends with `tests not found, language not read`, so the writer looks. A class that the change creates inside a `modified` file gets no such step. A test case that a designed test of the group covers is removed and not kept, so the step adds no copy of a test.
- In the group of each `modified` class whose path now reaches a new outside call, an exit whose class the change creates or whose method the current file of its class does not hold, the script writes 1 step in the migration stage tests, also where the signature of the class stays: `updates the tests that reach <outside interfaces> through <Class>: <files>`. The files are the test files that hold the name of the class or of a class of the model whose path reaches it, such as the controller of its entry. Where the search finds none, the step names the entries whose path reaches the class, because a test that runs an entry by its route names no class: `no test file names it or a caller of it; find the tests of <entries> by hand`. For a language outside the 4, or with no `--repo`, the step ends with `tests not found, language not read`.
- A created folder is a step of the migration stage folders alone, and never a step of the migration stage created classes.
- A modified file of framework wiring, such as an XML file, holds no class that the model can state, so the script writes 1 step for it in the migration stage bodies: `not modelled: edit <path> by hand (framework wiring)`. The step joins the lowest migration group of the classes whose `file` stands under the folder of that file, and group 1 where no class does.
- A step of the migration stage created classes writes the class with the bodies of its methods in the same step, as `creates <file> with <classes> and the bodies of <methods>`, because a file of signatures alone does not compile in every language. The migration stage bodies holds only the bodies of methods of `modified` classes; the migration stages are an order of work, not points where the code builds.
- A `removed` child whose code moved, which is the old file that the `oldPath` of a `created` child names, joins the migration group of that created class, and its removal step, `removes the file <old>, whose code <new> now holds`, comes right after the step of that class in the same group, so no group ends with 2 copies of 1 class.
- With `--repo`, the script finds the current callers of each renamed or moved name in the tree, and writes a body step for a method of a `modified` class whose signature differs from the current tree. Each step of a moved file, of a renamed class and of a class created with `oldPath` also lists the files that import the class, and ends with `; updates the imports of <files>`, because such a class does not build in a language that imports by package until its callers import it by its new name and place.
