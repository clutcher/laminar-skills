# Laminar Code Review: how it works

This file answers questions about the review. The 5 steps of `SKILL.md` never need it.

The review judges the 3 qualities the book gives high-quality code: it "is simple enough for humans to understand and change, works correctly as intended, and performs adequately for its purpose". Simplicity is judged from the reader's side, by the 6 cognitive failures. Correctness is judged as prevention, the design decisions that exclude errors, and as detection, the tests that verify behavior. Performance is judged as waste. The 2 principles, encapsulation and single level of abstraction, give the fixed direction of a simplicity fix, and they are not what the review judges by.

## The 5 stages of the review

| Stage | Who runs it | What it writes |
|---|---|---|
| Prepare | step 1, the 2 script commands | `code-graph.json`, from the extract command: the abstractions of the repository, the relations between them, the change and its marks on the abstractions. Then, from the prepare command, `review-abstractions.json`: the abstractions under review with their scale, change, visibility, lines, boundary rank, measures, facts and the results of the walks over the graph. Then `prepare.json`, `prepare-return.json` and `prepare-return.workflow.js`, which holds the same object for the judge workflow: the checks per abstraction per track, the screen batches, `io-summary.md`, and `code-under-review/`, 1 file per judge call, and `cost-plan.json`: the judge calls per judge type, per scale and per folder, their new tokens up to and after the screen, the cost of a run of the application, module and class scales only, and whether the plan is above the threshold |
| Screen | `review-screen-presence`, 1 screen call per batch of abstractions, and `review-screen-io`, 1 screen call for the I/O rules and 1 more where a group holds an end call no rule covers, all inside step 2 | presence answers per abstraction, which the workflow reads against the checks of each judge call, and I/O rules by type or module, which the workflow applies to every end call |
| Judge | 1 judge call per abstraction and judge type, or per design relation, application, boundary path or end method, all in 1 parallel run per wave inside step 2 | the possible findings of that judge call, and from the test plan also the main paths a test already runs. Nothing is returned for a check that finished with no finding |
| Verify | step 3's merge, which checks every quoted line, then `review-refuter` and `review-verifier` in step 4 | `merge.json`, `draft.md`, `draft-lines.md`, `merge-return.json`, `merge-return.workflow.js`, which holds the same object for the verify workflow, 1 refute file per possible finding under `refute/`, 1 verify file per item under `verify/` and, where an end method is unknown, `io-unknown.md`; then 1 refutation per possible finding the refuter reads, refuted or not refuted, and 1 verdict per refuted possible finding, keep, lower, combine or reject |
| Report | step 5's render | `review.md`, `review-evidence.md`, `review.sarif` |

**The whole of what a judge reads is 1 file the script wrote**, `code-under-review/<id>-<judge type>.md`: the abstraction, its change kind, the sections of its code slice the checks of that judge call read, with line numbers, and the places the walks found. The judge call names that file, the checks to answer and, where a check waits for the screen, the screen's answers. The file holds only data under short labels, and the body of the agent that reads it says what each label means. The workflow applies the screen's answers itself, and an abstraction the screen emptied of every check spawns no judge. A refuter call is given 1 file the same way, `refute/<number>.md`, and a verifier call is given `verify/<n>.md`, where `<n>` is the number of the item.

**The walk plans checks on the boundary.** An abstraction the change created or whose boundary it moved is judged at its own scale. An abstraction whose internals changed hands the walk down, until the walk reaches a created boundary or the body of a method. A trivial hunk gets no check: an import reorder, formatting, a version bump, a moved block with no new name, a generated file. A build file the change edits, such as `pom.xml`, `package.json`, `build.gradle.kts`, `setup.py` or `mix.exs`, holds no abstraction and gets no check, because the build tool fixes its names and a reader of the code does not design them; a folder where every changed file is a build file gets no module either; the extract line counts it under `build file(s) left out`, and `review-abstractions.json` lists it under `notParsed`. A YAML or a properties file is read as a key tree: a key that holds other keys is a class whose display name is its dotted key path and whose fields are the keys under it, the keys the change created under 1 key are 1 named value, and only for simplicity. A key the change created is judged, and so is the key right above a key the change created or removed; a key whose value alone changed is not judged, and 1 file gives at most 12 keys with children.

**The script finds every place before any agent reads.** The reference lines, the occurrences, the measures and the facts are computed in code from the graph, so no agent pays for a search a script could run.

**A check with no finding is never written and never paid for.** A judge returns possible findings only. The merge gives every check the Prepare stage planned 1 of 3 states: finished with a finding; finished with no finding, by a judge or by the screen; or failed, which means no judge answered it. It drops any possible finding whose quoted line is not in the code, after it repairs a quoted line a judge read from the numbering of its own code under review.

## The 5 tracks

Simplicity and Design judge simplicity, Design on design relations of 2 or more abstractions; Correctness · Prevention and Correctness · Detection judge correctness; Performance judges waste. The unit of each track is the book's own. Most check names are the book's own words. Leaked Details, Test Behavior, Integration Test Needed, Unit Test Needed, Unit Test to Remove and Partial Path Test are names of this review, each built on a rule of the book.

| Track | The unit, in the book's words | What it reads with the unit | Checks |
|---|---|---|---|
| Simplicity | an abstraction, "a simplified representation of something, with a boundary that exposes what is relevant and hides the rest" | the abstraction against its own internals, and the decision it holds against every other place that holds it | S1 Incomplete Mental Model, S2 Prediction Failure, S4 Compression Failure, S5 Unnamed Part Failure, S6 Open Construct Overload |
| Design | a design relation of 2 or more abstractions, because "For each abstraction you decide three things: what belongs inside it, what its boundary exposes, and what its name tells the reader" | a group of chains of called methods, a parameter type with every operation that takes it, a core operation with its neighbors, an in or out operation that decides, a method that rebuilds a value it takes, or a class with the member groups of its private members | D1 Over-Extraction, D2 Scoped Parameters, D3 Leaked Details, D4 Missing Boundary |
| Correctness · Prevention | the same abstraction, read "at the point where an abstraction is defined, because the types and design choices there decide which errors its callers can make" | the abstraction with its callers, and for CP6 the boundary path | CP1 Exclude Illegal States, CP3 Protect the State, CP4 Remove Edge Cases, CP5 Remove Hidden Dependencies, CP6 Validate at the Boundary, CP7 Fail Fast |
| Correctness · Detection | a test, "code that executes application logic with known inputs and checks that outputs match expected results" | the test with the code under test, and the tests of an application with the paths the change created or altered | CD2 Test Behavior, CD4 Integration Test Needed, CD5 Unit Test Needed, CD6 Unit Test to Remove, CD7 Partial Path Test |
| Performance | waste, "extra data movement that a known alternative avoids while preserving correctness, and that you can identify from the code without measurement" | the changed code with what it calls | P1 Looped I/O, P2 Repeated Retrieval, P3 Excess Retrieval, P4 Resource Recreation |

The track order, in the report and everywhere else, is Simplicity, Design, Correctness · Prevention, Correctness · Detection, Performance.

## What each judge reads

**Simplicity.** `review-judge-simplicity-variable`, `-method`, `-class` and `-module` judge 1 abstraction of their scale. A module is read as its own tree: the module root the script found, the boundary it declares, the folder 1 folder down with what each child exposes, and the imports into other modules; where the script finds no root, the judge reads the folder the change touched. `review-judge-simplicity-comment` reads only the comments of 1 production abstraction, each with the code line below it, and answers S2 and S5; a change with no comment makes no judge call. `review-judge-simplicity-decision` runs only where the walk found another place that may hold the same decision, reads the ranked list of places, and answers S1, the incomplete mental model. Have a Single Owner is the fixed direction of an S1 finding, never the check.

**Design.** 4 judges, 1 for each check, judge design relations the script builds in code, and only where the target is a repository; the Leaked Details judge also reads 1 method alone where it is an in or out operation that decides, or a method that rebuilds a value it takes. A chain group starts at each method the change touched and walks down the methods it calls, up to 3 steps, and stops at a method that code outside the chain also calls; it is judged only where it holds a called method whose every caller is inside the chain, and `review-judge-design-over-extraction` answers D1 Over-Extraction on it. A parameter type the change created or changed, with every operation that takes it and the members each reads, where the change added a member some operation never reads, goes to `review-judge-design-scoped-parameters`, which answers D2 Scoped Parameters. A core operation, an operation of the core of a module that code outside the core calls, with up to 3 neighbors, goes to `review-judge-design-leaked-details`, which answers D3 Leaked Details where the screen says its name or its signature names how the work is done rather than a business thing, or where it takes the result of another core operation. A method that takes a value of a repository type, returns that type and reads no field of its class goes to the same judge and answers D3. The core is found from the imports, never from a folder name. A production class that the change created, or whose member groups it touched, goes to `review-judge-design-missing-boundary` where its private methods and fields form 2 or more member groups, each joined by a field or a type that no exposed method uses; the judge answers D4 Missing Boundary where a group serves a part that the class never names. A Design finding leads with the cognitive failure and then the name of its check in brackets: `Working Memory Overload (Over-Extraction)`, `Prediction Failure / Incomplete Mental Model (Scoped Parameters)`, `Prediction Failure / Unnamed Part Failure (Leaked Details)` and `Unnamed Part Failure / Working Memory Overload (Missing Boundary)`; the leaked details are named so because such methods "are details that leaked into the wrong abstraction, and they belong elsewhere: above as a coordinator, or below as a detail". A Design finding proposes a merge or a split only where the code shows the parts it rests on, never chooses the form or a name, and asks the author where the reason does not stand in the code.

**Entry boundaries across applications.** Where the repository holds 2 or more applications, `review-judge-design-entry-boundary` reads the entry boundaries of 1 schema type or 1 controller the change created or changed, with the callers the script found by name in other applications of the same repository, at most 6 per judge call and 12 judge calls per run. It answers S1, where a caller decides again what the entry boundary decides; CP1, where a caller compares a free-text value from it with fixed values; and D3, where a caller decides a business rule on a value it receives from it. Each finding is marked `Across applications`. Callers in other repositories are not seen, and the report says so.

**Correctness · Prevention.** `review-judge-correctness-prevention` answers CP1, CP3, CP4, CP5 and CP7 on 1 abstraction. `review-judge-correctness-validate-at-the-boundary` answers CP6 Validate at the Boundary on 1 boundary path: a production method or class that takes a value, with the callers above it up to 3 entry methods and at most 4 calls, and up to 3 calls below it that leave the process; at most 24 judge calls per run.

**Correctness · Detection.** `review-judge-correctness-simplicity-test-method` reads every test method the change created or changed, and answers in 1 judge call the prediction failure on its name, the compression failure on its body, the unnamed part failure on its parts, and CD2 Test Behavior; each finding prints under its own track. A test name lets the reader predict the outcome and the condition where it takes the book's form `should<Outcome>When<Condition>`, in the written form of the language. A test class is judged by `review-judge-simplicity-class`, and 1 test class per production class "remains a reasonable place to start", never a finding on that ground alone.

`review-judge-correctness-test-plan` runs once for each application the change touched, the nearest folder above a class that holds a build file, and answers CD4 Integration Test Needed, CD5 Unit Test Needed, CD6 Unit Test to Remove and CD7 Partial Path Test. An application whose build files declare no test runner and which holds no test file is an application with no test runner: where the change touched its code, no test plan judge call runs for it, and the script writes 1 CD4 Integration Test Needed finding on the application folder, at application scale with confidence high, which no refuter and no verifier reads. The script reads the test runners of npm, Maven and Gradle, from the build files of the application and of the folders above it, and an npm `test` script counts unless it is the one `npm init` writes. For every other build tool the script writes no such finding, because Go, Rust, Python and other languages can run tests with no runner that a build file names. Its boundaries are the production classes the change created or changed that hold a method of their own; where its slices pass 1,000 lines, the script splits the judge call by module root and puts whole modules into each boundary group. To find the tests, the script starts at each boundary and its supertypes and walks up through the classes that name each one, within 30 seconds shared by the review, and links a test whose file name holds the class name with a test marker, or a test that names the class. The classes at the top of each walk are kept as top classes, at most 5 per boundary. Every test file the change touched goes into the change list whether the walk linked it or not. A main path a test already runs is no item: the judge returns it as a covered path. The merge numbers each covered path after the possible findings and writes 1 refute file for it, with the entry, the test, the outcome, the lines it rests on and the rules of its check; a refuter tries to show that the test does not run that path, and where it says refuted, the verifier rules keep or reject. A rejected covered path prints nowhere as covered: the render turns it into a CD4 Integration Test Needed finding on its entry, with its outcome, the fact of the rejection and the confidence of a CD4 item, because a wrong covered path hides a missing test. In patch mode only the patch is searched, and a CD4 or CD5 item has confidence `low`.

A production class whose tests the walk linked also carries the test friction found in them: a setup block that grew, a partial substitute, a substitute that returns another substitute, a private method reached from a test. The class and method judges read it as evidence of the unnamed part failure, never as a finding on its own.

**Performance.** `review-judge-performance-abstraction` answers P2, P3 and P4 inside 1 abstraction. The search for I/O follows the calls from each loop the change added or edited, and up from each changed method to a loop that runs it, through the methods of the repository until a call leaves the repository's own code. These are the end calls, and the method that holds one is an end method. A loop that does not run once for each item, such as a retry or a poll, starts no walk. A walk has no depth limit, no chain limit, no method limit and no time limit. The script names the outside type or module of each end call where the declarations and imports show it, and groups the end calls by it in `io-summary.md` with the dependency lines of the repository. `review-screen-io` reads that summary in 1 screen call and writes I/O rules, each on a type or a module, with callee patterns and the answer io or not io; an I/O rule never rests on a callee name alone. The workflow applies the I/O rules in code. An end method that holds an end call an I/O rule marks io goes to the judge. An end method with an end call no I/O rule answers, and no io end call, is unknown: no agent reads it, and the merge writes it to `io-unknown.md` in the run folder. `review-judge-performance-io-paths` then runs once for each end method that holds an io end call, reads every loop that reaches it, and answers P1 Looped I/O and P2 Repeated Retrieval. The I/O rules are kept for 30 days in a cache keyed by the dependency files, the repository and the script version.

## What the review produces

The merge and the render commands are code, so **no agent rewrites a finding on its way to the reader.**

**`review.md`, the reader's list.** A banner with the counts, then 1 line the render writes in code from the change, which names what the change created, moved, removed and changed, then the findings the review kept, then `## To consider`, then `## Limits`. Where the change holds a file that no language driver reads, 1 `**Not read**` line after the banner and the scope line names each such file. Where the run is limited to some scales, the render leaves out of the report every finding and every consideration at a scale the run did not ask for. The scope line then names each scale the render left out with the number of findings it left out, as `scales: application, module, class · left out: method 5, variable 0`, and `review.sarif` holds the same numbers under `leftOut` of its `scope`. `review.sarif` always writes `scales` under `scope`, in upper case: the scales the run asked for, or, where the run asked for none, every scale a judge reads, which is `APPLICATION`, `MODULE`, `CLASS`, `METHOD` and `VARIABLE`. A `review.sarif` from before 0.70.0 that has no `scope` is from a run at every scale. A judge that reads a whole application, such as the test plan, places a finding on the method it names, so the render can leave out a finding of that judge at method scale. A run at every scale reports that finding. The findings are sorted by track, then production code before test code, then by check, scale and file. Each track that holds a finding gets a `## ` header in the track order, and under it a `### Production code` or `### Test code` sub-header. The Correctness · Detection section ends with `### Already covered`, 1 line per main path a test already runs. A covered path that no refuter call or no verifier call settled ends its line with `(not verified: the second read did not finish, so this is as its judge wrote it)`. The numbering runs on across every section. Where the review found nothing, 1 `## Findings` header stands over the sentence that says so. A finding is in the change where a line the change added, altered or removed causes it or makes it worse; the paragraphs on `review.sarif` below say what the merge decides it from. **The `Direction:` line is fixed per check, and the script prints it, never an agent.** Each check has 1 short line, mapped by the check id, with overrides: by judge type for Prediction Failure and Unnamed Part Failure of the comment judge and of the test method judge, Unnamed Part Failure of the class judge and of the module judge, and Leaked Details of the entry boundary judge; by design relation for Leaked Details on a rebuilt value and on an in or out operation; and by scale for Integration Test Needed at application scale. The override by design relation comes first, then the one by judge type, then the one by scale. A finding the script settles in place of a judge takes the override of that judge. The line holds the principle that leads the fix, encapsulation or single level of abstraction, and then the move in a few words, which names both moves where the book allows both. A check of the tests prints no principle. Where the right form of the fix rests on a reason the code does not show, the judge asks it under `To confirm:` and never chooses the form. A consideration prints the line as `Direction, if this is a defect:`. Each item is 1 line and its sub-points:

```markdown
1. Method `isBarredFromSailing` in `Vessel`
   - Incomplete Mental Model: Vessel decides a failed spot check bars sailing, and the console badge decides the same again from the raw flag.
   - Direction: Encapsulate: give the decision 1 owner that every place uses, or drop a copy that no place needs.
   - Also in `VesselStatusBadgeComponent#labelFor`.
   - Confidence: Moderate. To confirm: Confirm that the console's VesselSummary is built from the ferry's Vessel data and that the badge label must match isBarredFromSailing; that join sits outside the code under review.
```

**Every possible finding gets a second read, unless the list below leaves it out.** A refuter call reads 1 possible finding with the rules of its check and the code under review, and tries to show it wrong. A possible finding the refuter does not refute is kept as the judge wrote it. A refuted possible finding goes to the verifier, 1 verifier call per item, which rules keep, lower, combine or reject on it. The verifier never raises a confidence and never turns a finding into a consideration or back. Where 2 or more checks of 1 item rest on the same lines and name 1 missing decision, the verifier can combine them into 1 finding with 1 lead line that names every check, joined by ` / `, and the fixed direction of each check it combines.

No second read is sent for a consideration, a finding of the test plan judge or of the I/O paths judge, or a finding the scripts settle themselves; each prints as it was filed. A covered path is sent to a second read like a possible finding. Where no refuter call or no verifier call answered in 2 attempts, the finding is not verified: it prints as its judge wrote it, with the line `- Not verified: the second read did not finish, so this is as its judge wrote it.`

```markdown
2. Method `getCurrentVoyage` in `CurrentVoyageService`
   - Remove Edge Cases / Fail Fast: The voyage is read from the session store and cast with no check, so a missing or wrong value has no decided behavior.
   - Directions:
     - Remove Edge Cases: Encapsulate: return a normal result for the special case, such as an empty list, or reject it early.
     - Fail Fast: Encapsulate: stop and signal the failure.
```

**`## To consider` holds the questions the code cannot settle, and each is a question to the author, not a finding.** An item goes there in 3 cases: its whole cause sits in lines the change did not touch, and it carries ` · existing code` after its name; the merge finds that a repeated decision rests only on places in other applications, or only on types that share most of their members; or a judge marks it as a trade-off or as a form that passes review. A copy of a decision in another application is always a question, whatever the 2 sides are, because only the author knows whether the copy is kept on purpose: it is a consideration that names the line that would show the 2 applications must give the same answer, and never a finding with a confidence; a place inside the lines of the reviewed abstraction itself does not count, so a copy in another method of the same file stays a copy in the same application. A consideration has no confidence: its lead line asks the question, `Found:` says what the review found, and it prints as it was filed, with no second read. The numbering runs on from the findings.

```markdown
3. Method `isHeldAtCustoms` in `ReleasePlanner`
   - Incomplete Mental Model: Must applications `dispatch` and `tracking` always give the same answer for the system to stay correct, or is the copy kept on purpose, such as to save a remote call or to check the same input on both sides?
   - Found: The customs hold rule is decided in dispatch and again in tracking.
   - Direction, if this is a defect: Encapsulate: give the decision 1 owner that every place uses, or drop a copy that no place needs.
   - Also in `CustomsHoldPolicy#isHeldAtCustoms`.
```

**The reader's list names abstractions and no places.** No item carries a file or a line; the places stay in the evidence file and in the machine file. **An `Also in` line names every other place of the finding by its enclosing abstraction**, as `Type#method`, or by its file and first line where no abstraction encloses it. On an S1 finding it names every place the decision judge read as holding the same decision. **A `Declared by the schema` line names the schema type whose code form the finding is on**, such as a GraphQL input that a resolver takes as a parameter of its own type: the review judges the code form, where the operations are, and the schema type is the contract the application publishes and the place the fix starts. It is never a second finding and never an `Also in` place; the evidence file gives its file and its line.

**`review-evidence.md`, the evidence file.** Every kept finding again with its check id, the cognitive failure, the prevention decision, the test check or the waste behind it, its full evidence quoted with its file and its line, the prediction it was read against, the confidence, a `Cause:` line, and its second read: a `Refutation:` line with the answer, the line, the rule and the reason; a `Verdict:` line where the verifier ruled; and a `Not verified:` line where no refuter call or verifier call answered. After the banner, `## The change` holds the same line about the change that the reader's list holds. The Correctness · Detection section ends with `Covered paths:`. `## To consider` follows the tracks, and each of its items carries a `To consider:` line with its question in place of the confidence. Then `## Rejected`, `## Not verified`, `## Verdicts with no item`, `## Dropped`, `## No finding, by a judge`, `## No finding, by the screen`, `## Failed`, `## Not checked`, `## Not scheduled`, `## I/O ends` and `## Sweep`, which hold what each name says. `## Rejected` also lists each covered path the verifier rejected, with its refutation and the fact of the rejection, and its CD4 finding prints in the Correctness · Detection section with a `Covered by, a claim the verifier rejected:` line. `## Not verified` lists the findings and the covered paths no refuter call or verifier call settled, and then, apart, the findings that were not sent to a second read. `## Not checked` says which paths the caller excluded, and then lists each changed file the review did not check, such as a build file or a file whose change is trivial, with the reason on its own line.

**`review.sarif`, the machine file.** One `result` per finding: `ruleId` is the check id, such as `S2` or `CP7`, and a combined finding lists every check under `rule_ids` in its property bag. The check id is the identity of a check: a later version can reword the lead words in the `name` of a rule and in `message.text`, so a tool that matches findings across runs matches them on `ruleId` and never on the lead words. In each result, `message.text` is the lead line and then the summary, a text that a reader stores and shows and never matches; the primary place is `locations`, every second place is `relatedLocations`, and the abstraction is a `logicalLocation`. The fixed line of each check is the `help.text` of its rule, and the fixed line of a finding is `direction` in its property bag. The confidence sits in the property bag with a fixed rank of 0.9, 0.6 and 0.3, as a rendering and never as a judgment; a finding with no confidence has the rank 0.9. The `scale` in the property bag, the `scales` under `scope` and the keys of `leftOut` are in upper case, such as `MODULE`. `baselineState` is `new` for a finding in the change and `unchanged` for an item in existing code. A finding has the SARIF level `warning`, and a consideration has the SARIF level `note`, no `rank`, no confidence, and `to_consider` and the summary in its property bag, with the question as its `message.text`. It is written to the SARIF 2.1.0 schema.

**In the change, and the kinds of change, for a tool that reads `review.sarif`.** The property bag of each result holds `changeKind`, the public change kind of the abstraction of the finding: `unchanged`, `moved`, `modified` or `created`. Where the finding names other abstractions, `related_abstractions` lists each of them as `abstraction`, its display name, `role`, and `changeKind`. The role is `also` for an `Also in` place, `entry` and `exit` for the ends of a test plan path, and `taken by` for an integration test that takes the branches of a unit test to remove. It names only the places of these 4 roles that have a display name. Each place in `relatedLocations` holds `changeKind` in its own property bag, and its `message.text` gives its role where it has one: `declared by the schema`, `entry`, `exit`, `taken by`, `branch` or `branch: <outcome>`, `caller in <application>` and `fill in <application>`; an `Also in` place has no role text. A related place that is a folder carries the kind of that folder.

A file has the kind created where the change added it, moved where the change only moved or renamed it, and modified where the change edited a line of its code. A folder has the kind created where the change created it, and modified where the change added, removed, moved or renamed a file in it; a folder that a file left is modified too. A folder whose files only had edits inside them stays unchanged, but the review still judges it at module scale where the change altered what it exposes. Where `--kind-base` is given, every kind is read against that revision. A review of named files alone, with `--files` and no `--range`, has no base, so every kind is `unchanged`.

`baselineState` is the answer of the review on whether a finding is in the change. The merge marks a possible finding in the change where a line it quotes is a changed line or stands next to removed lines, where its abstraction was created, which with `--kind-base` means created since that revision, or where its judge marked it so; the changed lines are those of the range, or those since the kind base where `--kind-base` is given. A module finding is in the change where its folder, or a file or a subfolder it names, has the kind modified or created. The verifier can set the mark again, and an item is in the change where 1 of its possible findings is. Every other item is in existing code: the review turns it into a consideration with ` · existing code` after its name, and in `review.sarif` it has `to_consider` true and `baselineState` `unchanged`. The kinds above explain that answer, and do not hold all of it, because the quoted lines and the marks do not stand in `review.sarif`. So a tool that reads `review.sarif` reads `baselineState` to know whether a finding is in the change, and never derives that from the kinds; it reads the kinds to show what changed beside the finding and to choose what to do with it.

**There is no severity, no ranking and no cap.** Every finding is a must, or it is not a finding. A finding carries a confidence instead, which says only how sure the review is that the defect exists, and says what would confirm the cost where that confidence is not high. A question the code cannot settle is never a finding: it goes to `## To consider`.

## How many judges run at once, and waves

A workflow runs at most the smaller of 16 and the CPU count minus 2 agent calls at once by default. The session setting `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` raises that, up to 256, and a large review runs about as many times faster, until the account's rate limits throttle it. One run of a workflow holds at most 1,000 agent calls, so the Prepare stage plans the judge calls in waves of at most 900 agent calls each and keeps every judge call with the screen batch and the I/O rules it needs; the agent calls left below the limit are for judge calls that are tried again. The merge splits the second read the same way: a verify wave holds whole items whose possible findings for the refuter add up to at most 450, so its refuter calls and verifier calls stay at 900, and each refuter call and each verifier call is tried at most 2 times. The cost plan of the Prepare stage counts the refuter calls and the verifier calls it expects, so the cost check covers the second read too.
